A release produces three distributions: `mizuoto` (wheel and sdist, with the built web UI inside, every engine under a permissive licence included) and the wheels of the two licence-gated engines, `mizuoto-fishspeech` and `mizuoto-indextts`. All three install into one environment over a torch the user chose, and each is versioned, checked and released on its own. This page covers how they are built, checked and published to PyPI (with twine, by the release workflow).

## Dependencies

Mizuoto is one environment: the dependencies of the core, the API, the command line, the web UI and every engine are in `pyproject.toml` and install at once. Every new dependency must answer three questions: does it have wheels for every platform CI covers (Linux x86_64, Windows x86_64, macOS arm64, CPython 3.10–3.14), does it change results, does it change process-wide state.

### Required

| For | Packages | Notes |
| --- | --- | --- |
| Web and command line | fastapi (≥ 0.115.3), starlette (≥ 0.40), uvicorn, websockets, python-socketio, pydantic 2, httpx, typer (&lt; 0.28), rich, tomli-w, tomli (Python &lt; 3.11), send2trash | Starlette 0.40's `FileResponse` honours Range, so the player seeks; uvicorn speaks WebSocket only with websockets installed; typer has an upper bound because the command line uses its private modules |
| Audio | av (PyAV), numpy | Decoding, encoding and resampling through PyAV, the rest with numpy; no ffmpeg or sox program is called |
| Runtime | torch (≥ 2.8), safetensors, soxr, tokenizers | torch's build is the user's (below); soxr is the resampler librosa calls; tokenizers builds the BPE transformers builds |
| Text | pypinyin, rjieba, jieba, opencc, kaldifst, inflect, tiktoken, regex, wordsegment, budoux, ToJyutping, fasttext-predict (fasttext-predict-v2 on Python 3.14: the same sources, released with 3.14 wheels), pyyaml | Many versions are **pinned** (`pypinyin==0.55.0`, `opencc==1.4.2`, `inflect==7.3.1`…): the engines' output depends on them, and another version changes phones and audio |

The licence-gated packages bring a few of their own: `mizuoto-fishspeech` needs tokenizers and safetensors, `mizuoto-indextts` sentencepiece. Each also names the packages it imports directly that Mizuoto already brings (torch and numpy; `mizuoto-indextts` also pyyaml and tiktoken), with Mizuoto's bounds, so its dependencies do not rest on Mizuoto's.

### Optional extras

| Extra | Packages | For |
| --- | --- | --- |
| `mizuoto[gptsovits-ja]` | `pyopenjtalk==0.4.1` | GPT-SoVITS's Japanese front end; published as a source distribution only, so installing it needs CMake and a C++ compiler |
| `mizuoto[gptsovits-ko]` | `python-mecab-ko==1.3.7`, `jamo==0.4.1` | GPT-SoVITS's Korean front end (python-mecab-ko's wheels stop at Python 3.12; later Pythons build it against mecab-ko) |
| `mizuoto-indextts[ja]` | fugashi, unidic-lite | IndexTTS-2.5's Japanese segmentation |

Without an extra, text in that language fails with `capability_not_supported` and the install command in the hint; `mizuoto doctor` lists each engine's missing extras too. The optional attention packages (flash-attn, xFormers, SageAttention) are not extras: they must match the user's torch, and `mizuoto doctor` prints install commands that keep the installed torch (`--no-deps`); see [Attention acceleration](/docs/development-acceleration).

| pynini, WeTextProcessing, wetext, modelscope | kaldifst with exported FSTs (shared assets, or shipped in the package) |
| jieba_fast, g2p_en, nltk (and the data it downloads at run time) | jieba; the ported GRU and tagger, with their data shipped |

### torch and platforms

torch is a dependency, but its build is installed by the user first: from the download.pytorch.org index that matches the machine (CUDA, ROCm, XPU or CPU; on Apple silicon PyPI's wheels include MPS), then Mizuoto, whose installation keeps it. `mizuoto/core/compute/torch_index.py` knows the builds published for torch ≥ 2.8 (CUDA cu126–cu132, ROCm 6.4–7.2, XPU, CPU) and picks the newest CUDA build the driver runs, else ROCm, XPU, MPS or CPU; `mizuoto doctor` prints the install command when the installed build does not match the hardware.

| Device | Platforms |
| --- | --- |
| NVIDIA (CUDA) | Linux, Windows |
| AMD (ROCm; `cuda` to torch) | Linux |
| Intel (XPU) | Linux, Windows |
| Apple silicon (MPS) | macOS arm64 |
| CPU | All |

CI tests every combination of Linux x86_64, Windows x86_64 and macOS arm64 with Python 3.10–3.14 on CPU torch, and separately torch 2.8.0 and the latest release.

<Callout type="warn" title="ROCm, XPU and MPS">
The code has paths for these devices (device probing, float64 modules on the CPU where a device lacks float64, no compilation on MPS, CUDA graphs and half precision only on CUDA) and they are tested on simulated devices, but they have not been verified on AMD, Intel or Apple hardware.
</Callout>

## Versions

Each distribution has a version of its own, in a file that holds nothing else; a push to `main` that changes it releases that distribution (see [below](#ci-and-the-release-workflow)):

| File | Version of | Tag |
| --- | --- | --- |
| `mizuoto/version.py` | `mizuoto` (the web UI's `package.json` follows it by hand) | `v<version>` |
| `packages/native/fishspeech/mizuoto_fishspeech/version.py` | `mizuoto-fishspeech` | `mizuoto-fishspeech-v<version>` |
| `packages/native/indextts/mizuoto_indextts/version.py` | `mizuoto-indextts` | `mizuoto-indextts-v<version>` |

A gated package names the Mizuoto versions it works with in its `pyproject.toml`: `mizuoto>=0.2.0,<0.3`. Its code runs on Mizuoto's runtime and its manifest (options, catalogue, licence) ships in `mizuoto`, so:

- **The lower bound** is the oldest Mizuoto release with everything the package uses. CI tests the package on that release from PyPI (the `oldest-mizuoto` job); raise the bound when the package starts using something newer, and release Mizuoto first.
- **The upper bound** is the next minor release while Mizuoto is 0.x. `check_gated_distribution` (in `tests/core/test_engines.py`, run by each package's `test_<id>_package.py`) fails once Mizuoto's version leaves the range, so a Mizuoto release past it also releases the gated packages with a raised range.
- **A change to a gated engine's options** changes its manifest in `mizuoto` too: release Mizuoto with the manifest, then the package with its lower bound raised to that release.

`mizuoto doctor` reports an installed gated engine that does not go with this Mizuoto (its range excludes it, or its `OPTION_SCHEMA` and the manifest disagree) as an error with `pip install --upgrade mizuoto mizuoto-<id>`, and `mizuoto version` lists each distribution's version.

<Callout type="info" title="What an upgrade changes on disk">
Voice caches are keyed by Mizuoto's version, and for a gated engine by its distribution's version too, so they are rebuilt once after an upgrade of either. Settings keys a version no longer knows are ignored (see [Architecture](/docs/development-architecture#settings)). A host and its remote agents must speak the same protocol version (`AGENT_PROTOCOL`, now 2): otherwise each refuses the other at `hello` with an upgrade hint. More in [The data folder and compatibility](/docs/development-architecture#the-data-folder-and-compatibility).
</Callout>

## Wheels: `scripts/build_wheels.py`

```bash
python scripts/dev.py wheels                       # all: mizuoto and every gated engine, each at its own version
python scripts/dev.py wheels host                  # mizuoto only
python scripts/dev.py wheels native indextts       # chosen gated engines
python scripts/build_wheels.py host --skip-web --out /wheels
```

- **host**: `bun install --frozen-lockfile` and `bun run build` in `mizuoto/webui` (`--skip-web` reuses the existing `dist/`, as Docker's `wheels` stage does), a check that `dist/index.html` exists, then `uv build` of the `mizuoto` sdist and, from it, the wheel, from a clean copy of `mizuoto/`, `pyproject.toml` and `README.md` (no `__pycache__`, no stale `build/`).
- **native**: each package in `packages/native/` (or the ones named), copied without `__pycache__`, `*.egg-info`, `build` and `dist`, and built with `uv build --wheel`.
- The output goes to `dist/` by default. The script uses the standard library plus uv and bun.

The package data that ships in the wheel is listed in `pyproject.toml` (`[tool.setuptools.package-data]`): the built UI, the engine manifests, files manifests and licence texts, F5-TTS's vocabulary, GPT-SoVITS's text front-end data, Whisper's vocabulary. IndexTTS's text-normalisation FSTs ship in `mizuoto-indextts`.

## Smoke test: `scripts/smoke_wheels.py`

```bash
python scripts/dev.py smoke                        # same as python scripts/smoke_wheels.py --dist dist
python scripts/smoke_wheels.py --dist dist --python 3.13 --torch torch==2.8.0
python scripts/smoke_wheels.py --dist dist --others none   # only the wheels in dist/
```

It tries the built distributions as a user gets them. In a temporary folder outside the checkout, uv creates a new environment (`--python`, 3.11 by default), installs torch first from `--torch-index` (the CPU build by default; `--torch` picks the version, `torch>=2.8` by default), then, in one install, the wheels in `--dist` and the distributions it lacks from `--index` (`--others index`, the default), which must leave that torch in place. Since each distribution is released on its own, a release is tried with the others as users have them: a `mizuoto` wheel with the gated engines' released packages, a gated engine's wheel with the newest released Mizuoto its range allows. A Mizuoto release the released gated packages do not allow fails here. The installed versions must be the wheels'. uv runs without the machine's configuration (`--no-config`, no `UV_*`/`PIP_*` variables). Then, in a temporary data folder:

1. `mizuoto version`, `mizuoto env vars` and `mizuoto doctor`: every engine must be available;
2. every engine's implementation and trainer imported (`get_engine`), every module of `mizuoto` and the gated packages imported, and every data file the checkout has beside the code of the distributions built from it found installed (the ones engines read at run time actually read);
3. a dummy-engine `mizuoto speak`;
4. the server: `/api/v1/app/health`, the UI, and a dummy speak through the API.

## CI and the release workflow

`.github/workflows/ci.yml` checks each push and pull request for what it changes: Mizuoto, a gated package, the web UI, the docs site (see [Testing](/docs/development-testing#ci)).

`.github/workflows/release.yml` runs on a push to `main` that changes a version file (`mizuoto/version.py`, `packages/native/*/mizuoto_*/version.py`), on a pushed tag `v*` or `mizuoto-*-v*` (GitHub applies no path filter to tags) and by hand (its `packages` input: `all`, `mizuoto`, `mizuoto-fishspeech` or `mizuoto-indextts`). One release runs at a time per ref, and none is cancelled. Packages are installed with uv, as in CI.

1. `plan`: `python scripts/ci.py release` decides what this run releases. A push releases each distribution whose version file it changed (the compare API's files); a tag releases the one it names and must equal its version (`v0.2.0` for Mizuoto 0.2.0, `mizuoto-indextts-v0.2.1` for mizuoto-indextts 0.2.1); a manual run, its input.
2. `checks`: `ci.yml` itself, called as a reusable workflow, for what the push changed (a version file checks its distribution; a tag or a manual run, everything). CI's own run of the same push to `main` skips its jobs, so nothing runs twice.
3. `build` (Ubuntu, Python 3.11, uv; bun for Mizuoto's web UI): `build_wheels.py host` and/or `build_wheels.py native <id>…`, only what is released; `twine check dist/*`; `dist/` is uploaded as the `dist` artifact.
4. `smoke` (Ubuntu, Python 3.10 and 3.14): downloads the artifact and runs `smoke_wheels.py --dist dist --python <version> --others index`, so the release is tried with the other distributions as released on PyPI.
5. `publish`: in the `pypi` environment (which can require an approval), with the `TWINE_PASSWORD` secret (a PyPI API token; user `__token__`), `twine upload --skip-existing` of Mizuoto first, then the gated wheels, so a package that needs a new Mizuoto never appears before it. A version already on PyPI is skipped.
6. `github-release` (tags only): a GitHub release named after the tag, with that distribution's files and notes generated from the previous tag of the same distribution; a gated engine's release is not marked latest.

So the usual release of one distribution is: bump its version file, push to `main` (the release publishes it), then push its tag (`v<version>`, or `mizuoto-<id>-v<version>`) for the GitHub release (its upload finds the files already on PyPI). Bumping several version files in one push releases them together, Mizuoto first.

## Docker

The `Dockerfile` at the repository root builds one image: the server, its web UI and every engine, with GPT-SoVITS's Japanese and Korean front ends (and IndexTTS-2.5's Japanese with `GATED=1`). Models go into the `/data` volume.

```bash
docker build -t mizuoto .                                   # torch's CUDA 12.8 build
docker build -t mizuoto:cpu --build-arg TORCH_INDEX=https://download.pytorch.org/whl/cpu .
docker build -t mizuoto --build-arg GATED=1 .               # with Fish Speech and IndexTTS
docker run --gpus all -p 7869:7869 -v mizuoto-data:/data -e MIZUOTO_SERVER__ACCESS_TOKEN=change-me mizuoto
```

| Build argument | Default | Meaning |
| --- | --- | --- |
| `PYTHON` | `3.11` | The `python:<version>-slim` base of the wheels stage and the image |
| `TORCH_INDEX` | `https://download.pytorch.org/whl/cu128` | Where torch comes from: a CUDA (`cu126` … `cu132`), ROCm (`rocm6.4` … `rocm7.2`) or `cpu` index |
| `TORCH` | `torch>=2.8` | Which torch |
| `GATED` | `0` | `1` also builds and installs the licence-gated engines (their licences must still be accepted) |

| Stage | What |
| --- | --- |
| `web` | `oven/bun:1`: `bun install --frozen-lockfile`, `bun run build` |
| `wheels` | `python:<PYTHON>-slim` with a compiler and CMake: a wheel of `pyopenjtalk==0.4.1` (published as an sdist only), `build_wheels.py host --skip-web`, and `build_wheels.py native` when `GATED=1` |
| the image | `python:<PYTHON>-slim`: torch from `TORCH_INDEX` first, then the wheels with `mizuoto[gptsovits-ja,gptsovits-ko]` (and `mizuoto-indextts[ja]`), the rest from PyPI; `MIZUOTO_DATA_DIR=/data`, a `/data` volume, port 7869, a health check on `/api/v1/app/health` |

No system packages are installed in the image: PyAV, torch and the text libraries ship their native code in their wheels. Without a C compiler in the image, `compute.compile` runs eagerly (it warns once). For using the image, see [Docker](/docs/advanced-docker).

## The model mirror: `scripts/mirror_models.py`

`downloads.repository = "mizuoto-model"` makes Mizuoto download from its mirror repository first (`downloads.mirror_repo`, default `licyk/mizuoto-model`, the same id on Hugging Face and ModelScope) and fill in what the mirror lacks from each model's official repositories, so a partial mirror works. The mirror lays files out as Mizuoto keeps them: a model under `<engine>/<model>/<path>`, a shared asset under `_assets/<engine>/<asset>/<path>`.

```bash
python scripts/mirror_models.py build OUT [id…]        # lay the models folder out as a mirror
python scripts/mirror_models.py upload OUT --repo licyk/mizuoto-model [--modelscope]
python scripts/mirror_models.py check --repo licyk/mizuoto-model
```

- `build` lays the installed catalogue models and shared assets out under `OUT` (hard links where possible), checks each file against its pinned size and SHA-256 (`--no-verify`: sizes only), and writes `MIRROR.json` (each file's path, size, SHA-256 and official origin) and a README. Archive parts (`unpack`) are not kept after unpacking, so they stay official-only. Licence-gated engines are left out unless `--gated`.
- `upload` publishes with `hf upload-large-folder` (it needs `hf auth login`) and, with `--modelscope`, with `modelscope upload`.
- `check` lists, with HEAD requests, which catalogue files the published mirror lacks.

Publishing the mirror is the mirror owner's step; the weights keep their own licences.

## The docs site

This site lives in `site/`. It is built on fumadocs (TanStack Start + Vite) with bun into static files (`.output/public`). `.github/workflows/site.yml` publishes it to GitHub Pages: on a push to `main` that changes `site/` (or by hand) it runs the site's checks, builds it with `VITE_BASE_PATH=/Mizuoto/` (Pages serves it under `https://licyk.github.io/Mizuoto/`; the router and the search index follow Vite's base), adds `.nojekyll`, and force-pushes the output to the `gh-pages` branch over SSH with the `GITEE_RSA_PRIVATE_KEY` secret (a key with write access to the repository). The repository's Pages settings serve that branch. `site/vercel.json` is ready for a Vercel deployment at the root path.

```bash
python scripts/dev.py site-install   # bun install in site/
python scripts/dev.py site-dev       # local preview with hot reload
python scripts/dev.py site           # vite build, then scripts/prepare-static-output.mjs
python scripts/dev.py test-site      # vitest, then tsc --noEmit
```

CI's `site` job runs `bun install --frozen-lockfile`, `bun run check`, `bun run test` and `bun run build` in `site/`, for changes to `site/` only.

- Pages are in `site/content/docs/`: `<slug>.mdx` in Simplified Chinese (the default language, `zh-CN`) and `<slug>.en.mdx` in English, with the same structure. The sidebars are `meta.json` and `meta.en.json`, grouped by `---Title---` separators.
- The frontmatter has `title`, `description` and `icon` (a Lucide icon name). The MDX components are in `site/src/components/mdx.tsx`: `Cards`/`Card`, `Callout`, `Tabs`/`Tab`, `Steps`/`Step`, `Accordions`/`Accordion` and `Mermaid` (a `chart` prop; rendered in the browser with Mermaid loaded from a CDN, following the site's light or dark theme).
- `prepare-static-output.mjs` checks that every page in `meta.json` produced `docs/<slug>/index.html` and copies `_shell.html` to `404.html`.
- `src/lib/i18n-content.test.ts` requires an English page for every Chinese one and the same page order in both sidebars.
