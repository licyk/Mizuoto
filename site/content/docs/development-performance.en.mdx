Speed work on the inference and training code follows one rule: **the results do not change**. Every optimisation recorded here gives the same audio sample for sample, and the same losses and saved weights bit for bit, as the code before it on the CPU, where the engines' parity with upstream is established. On a GPU, "the same" means identical to the code before on the same GPU, driver, torch and settings. Faster paths that change the arithmetic are opt-in features, described in [Acceleration](/docs/development-acceleration); the user-facing settings are in [Performance](/docs/advanced-performance).

## How it is measured

| Tool | What it does |
| --- | --- |
| `scripts/parity/perf.py run <cases.jsonl>… --name NAME [--only ID] [--repeat N] [--device D] [--setting k=v] [--reference NAME] [--profile] [--torch-profile [--keep-trace]] [--deterministic]` | Runs parity cases through the whole stack in one process, each `--repeat` times (3): the first loads the model and prepares the voice, the others are warm. Records the wall time, load, first chunk, engine total, real-time factor, and the time inside each phase (`ctx.use` / `ctx.run`, exclusive of nested phases, plus the time outside phases). Compares the audio sample for sample across the runs and with `--reference`: an earlier run of that name, else the case's parity fixture |
| `perf.py compare --a NAME --b NAME [--report out.md]`, `perf.py show NAME` | The warm runs of two rounds side by side, the speed-up, the time to first audio of streamed cases and the phases that changed most |
| `scripts/parity/train_perf.py run <engine> --fixture F --name NAME [--device D] [--setting k=v] [--reference NAME] [--profile]`, `compare` | A fine-tune with a parity fixture's recipe through the whole stack, every stage a child process as in use: each stage's time, the time per step, every metric and the SHA-256 of every weight file the export wrote, compared with an earlier run |

- `--profile` adds an uncounted run under cProfile (in-process stages for `train_perf.py`); `--torch-profile` lists the operators by their own time.
- **On a GPU** (`--device cuda:N`, which becomes every engine's device, and training's): the harness waits for the device at each phase boundary, so a phase's time is its work and not only its launches, and records per phase the peak allocation, the working memory above what was allocated once the phase's weights were placed, and the working memory the engine asked for (with the call that came closest to its own estimate: a phase's largest use and largest estimate can come from different calls), with the request's peak allocated and reserved memory. `--torch-profile` then also records the device's activity and summarises it per phase (`<case>.gpu.json`): wall and device-busy time, kernels, launches, CUDA graph replays, host waits for the device (`cudaStreamSynchronize`, `cudaEventSynchronize`, synchronous `cudaMemcpy`; the harness's own two `cudaDeviceSynchronize` per phase counted apart) and host↔device copies.
- `--deterministic` runs with `torch.use_deterministic_algorithms(True, warn_only=True)` and `CUBLAS_WORKSPACE_CONFIG=:4096:8`, set by the harness (native code never sets process-wide state); operations without a deterministic implementation are listed in the record instead of failing the case. `train_perf.py --setting training.memory=low` measures a memory preset.
- Records go to `MIZUOTO_PERF_DIR` (default `~/code_workspace/experiment/perf`), one JSON file per case and round.
- A warm time is the fastest warm run: the machine's other work only ever slows a run down. Comparisons that matter are interleaved, the two codes in separate processes, one after the other.

<Steps>
<Step>

Freeze the code being measured (a worktree at the commit) and run the baseline: `perf.py run` over the case set, `train_perf.py run` for each trainer.

</Step>
<Step>

Profile (`--profile`, `--torch-profile`) to find where the time goes; for a kernel-level change, write a micro-benchmark and check the operation's output with `torch.equal` over the shapes the engines use.

</Step>
<Step>

Run the changed code with `--reference` set to the baseline: every case must give identical audio, every fine-tune identical metrics and weight hashes. Then run the parity stack for the engines whose code changed, and the test suite.

</Step>
<Step>

`perf.py compare` for the table; record the round here.

</Step>
</Steps>

The inference set is thirteen cases: Qwen3-TTS `base-clone-en` and `cv-en-aiden`, F5-TTS `clone-en`, OmniVoice `clone-en`, CosyVoice `v2-clone-en` and `v3-clone-en`, GPT-SoVITS `v2-clone-zh` and `v4-clone-zh`, Fish Speech `clone-en`, IndexTTS `v2-clone-en` and `v15-clone-en`, VoxCPM `v2-clone-en` and `v15-clone-en`. The training set is one fine-tune per trainer on an 11-clip dataset.

## Conditions

- **CPU**: AMD Ryzen 9 5900X (12 cores; torch uses 12 threads), 125 GB RAM, torch 2.8.0 with MKL 2024.2 and oneDNN 3.7.1, Python 3.11; fp32, except VoxCPM in bf16 (its upstream default). Other work on the machine takes about 9 % of its threads; a run whose compute thread is preempted stalls, so single runs vary by up to ±10 %.
- **GPU**: two RTX 3090 (24 GB), **shared with another workload** that held about 21 GB of each and kept both 100 % busy. Every GPU number below is inflated by that sharing; comparisons were interleaved on the same GPU and torch. Models that did not fit beside the other workload were measured as their decoding loop alone: the real sizes, random weights and a few of their layers, which is labelled where it applies.
- **GPU, from 2026-10-18** ([GPU baseline](#gpu-baseline-g0)): the same two RTX 3090, **free** (no other workload), driver 595.99.02, torch 2.8.0+cu128 (CUDA 12.8, cuDNN 9.10.2), PCIe 4.0 x16. Inference ran on one card while the fine-tunes ran on the other, so the two shared the CPU.

## CPU, round 1: CPU settings and exact clean-ups

| Change | Why it is exact |
| --- | --- |
| `compute.cpu_allocator` and `compute.cpu_threads` ([Acceleration](/docs/development-acceleration#cpu-settings)) | where memory comes from and where threads run, not what is computed; the same thread count splits the work the same way |
| VoxCPM attends over the cache up to the next multiple of 256 past the current length, mask kept, instead of all 8192 positions (on the CPU only, since G1: see [GPU checks](#gpu-checks-of-the-cpu-rounds-g1)) | masked positions add exact zeros, and the CPU's SDPA gives the same bits for any cut at a multiple of 64 (every length up to 3100, bf16 and fp32, batch 1 and 2) |
| DiT rotary embedding: cos and sin once per forward, no multiplication by 1, no concatenation of an empty tail (F5-TTS, CosyVoice 3, GPT-SoVITS v4/v5) | the same values |
| CosyVoice's flow U-Net builds its per-head mask once per forward, not in each of its 56 blocks | the same tensor |
| IndexTTS: GPT-2's GELU in place; a beam reorder that keeps every row skipped | the same operations in the same order |

## CPU, round 2: training

Profiles of the fine-tunes showed backward passes and products as everywhere, AdamW's per-tensor loop, dropout masks, and, for Fish Speech, 41 s of a 123 s training stage spent replaying about 18 billion 32-bit draws from the process-wide generator only to put it where upstream's is when training starts.

| Change | Why it is exact |
| --- | --- |
| The generator jumped ahead instead of drawing: MT19937's state after *n* draws computed in GF(2) (`mizuoto/training/rng.py`), 204 jumps in 2.3 s instead of 41–52 s | the state equals drawing's byte for byte (tested from 1 to 2·10⁹ draws) |
| Fish Speech's LoRA merged with one float32 copy of each base weight, not two | the same values |
| Fish Speech's codec `snake` in place when no gradient is taken | the same operations in the same order |

Fish Speech S2 Pro LoRA (2 steps): 207.4 s before the CPU rounds, 172–173 s after round 1, 128.5–130.6 s after round 2 (training stage 146.8 → 83 s), metrics and weights identical. Its warm request went from 110.4 to 85.7 s (the codec 3.3 → 2.0 s), its parity cases unchanged.

## The attention dispatcher

Routing every attention call through `mizuoto.runtime.accel` ([Acceleration](/docs/development-acceleration#attention)) costs about 1 µs a call under `auto`: +1.11 µs on a decode-sized call (16 heads, 1 query, 300 keys, head dim 128: 28.8 → 30.0 µs), +0.82 µs on a small one. The most calls a request made in the set is 7,152 (Fish Speech), well under 0.1 % of its time. All thirteen cases and all seven fine-tunes stayed identical; warm times moved within the machine's noise (Fish Speech, interleaved: 86.6/86.9 s before, 86.5/87.3 s after).

With `compute.attention = fast` on the CPU every call goes through the policy, all on SDPA, no fallbacks (calls per request: F5-TTS 704, OmniVoice 896, GPT-SoVITS v4 3,044, VoxCPM 1.5 3,928, CosyVoice 2 4,688, Qwen3-TTS 4,877, IndexTTS 2 6,667, Fish Speech 7,152). Seven engines still gave identical audio; IndexTTS 2 differed by at most 2 int16 steps (86.1 dB SNR, same length), its perceiver's hand-written softmax being computed by SDPA.

## GPU: decoding without waits, as CUDA graphs

Each autoregressive decoder launched thousands of small kernels per step one by one and waited for the device many times a step (`torch.multinomial`'s checks, masks copied at each step, padding masks read back, stop checks), so the CPU's launch time and the GPU's work added up. Each now waits once per step and, with `compute.cuda_graphs`, replays its step's kernels as CUDA graphs ([Acceleration](/docs/development-acceleration#cuda-graphs-computecuda_graphs)). Every result below is the old code's audio or tokens; the CPU parity cases of each engine stayed identical. All on the shared GPUs described above.

Peak MB is the request's peak allocation, every model loaded in the process included. GPT-SoVITS's streamed case decodes the whole text before its first chunk (first audio 0.95 s of 0.96 s); VoxCPM's streams by patch (0.14 s).

**Repeats.** Every case gives the same audio run to run and in a new process, in the default mode, except VoxCPM 2's first request. `--deterministic` changes the bits of CosyVoice 2, IndexTTS 2, OmniVoice and VoxCPM (other cuBLAS and cuDNN algorithms), repeats as well, and lists no operation without a deterministic kernel. So later GPU rounds compare outputs exactly in the default mode, with VoxCPM's first request thrown away.

**VoxCPM's first request.** Snake is a TorchScript function, as upstream's is. On CUDA, TorchScript's profiling executor runs a function's first call for a shape as separate operations (bit-identical to eager code and to the CPU), then runs a fused kernel that differs by up to 4.8·10⁻⁷. A shape it has not seen falls back to the unfused operations until it is profiled. So which calls are fused depends on what the process has already decoded, and a warm-up at load cannot make every request repeat. With the fuser off (an experiment; native code never sets it) the first request agrees with the later ones. The fuser also compiles its kernels on the default device: a process working on `cuda:1` opens a 256 MB context on `cuda:0` (seen in VoxCPM's and GPT-SoVITS's training, whose WaveNet gate is scripted too). The CPU is unaffected (no fusion there). (Since fixed: Snake runs eagerly, the same on every request and on the CPU; about 1 % slower in the VAE. See [VoxCPM](/docs/engines-voxcpm#deviations).)

**Where the time goes** (one extra run under torch's profiler, per phase: the device's busy time against the phase's warm time without the profiler, which slows the host's side):

- Bound by the device's work (about 90 % busy or more): F5-TTS's DiT, IndexTTS's s2mel, BigVGAN and 1.5's GPT, CosyVoice 3's flow, Fish Speech's, Qwen3-TTS 1.7B's, VoxCPM's and OmniVoice's language models. (Capturing OmniVoice's step forward as a CUDA graph, tried in G2, gave 2 %.)
- Bound by launches: GPT-SoVITS's GPT (about 56 %) and CosyVoice 2's language model (about 69 %).
- Host waits: about one per generated token in every autoregressive decoder (GPT-SoVITS v2 157 for 157 tokens, Fish Speech 92 for about 87 frames, Qwen3-TTS 82 for about 73 frames), as designed.

**Working memory** against each phase's estimate (the estimate must be at or above what the phase uses): language models use 2–17 % of their estimates (Qwen3-TTS's talker 28 MB of 328, Fish Speech's 128 of 733). Two decoders use more than estimated: IndexTTS 1.5's BigVGAN 326 MB against 279, VoxCPM 1.5's VAE 278 MB against 183; VoxCPM 2's VAE is close (190 against 203). The OOM retry covers these on a tight GPU; the estimates are to be raised.

## GPU checks of the CPU rounds (G1)

The code and settings proven only on the CPU, checked on the free GPUs of the [GPU baseline](#gpu-baseline-g0) (2026-10-18).

**Every change since before round 1, step by step.** The G0 set ran with the code of each step on one GPU (frozen worktrees, each with its own harness), and each step's audio was compared with the step before:

Fixed, so the GPU's audio is again the code before's:

- **VoxCPM's attention span.** On CUDA a step takes SDPA's math path, whose matrix-vector product and softmax split their sums by the key length: a cut at the next multiple of 256 (or 512 … 4096) differs from the whole 8192-position cache at most positions in bf16, fp16 and fp32. The span is now used on the CPU only (`minicpm.attend_span`); on a GPU a step attends over the whole cache, as upstream. Identical to the code before round 1 again, at a cost: warm requests 1.24 → 2.13 s (VoxCPM 2) and 0.68 → 0.96 s (1.5).
- **Fish Speech's in-place Snake.** On a GPU the codec runs under bf16 autocast, which computes `pow` and `reciprocal` in float32; upstream's Snake therefore ends in float32 while the in-place form, which keeps its buffer's dtype, stayed in bf16 (up to 0.1 apart). The in-place form now runs only without autocast; identical to round 1 again, at the same speed. The unit test covers autocast.
- **CosyVoice on `cuda:1`** faulted with an illegal memory access: its decoder-step graphs were captured and replayed while `cuda:0` was current, and a replay runs on the current device's stream. Captured and replayed under `torch.cuda.device(graphs.device)` now, as the other engines do ([Acceleration](/docs/development-acceleration#cuda-graphs-computecuda_graphs)).

The rotary tables, IndexTTS's in-place GELU and Fish Speech's Snake give their reference's bits on CUDA in fp32, fp16 and bf16 (the exactness tests now run on CUDA when a GPU is visible); CosyVoice's U-Net mask is the same tensor made once. Fish Speech's GPU training replays upstream's initialisation on the CPU generator, as upstream builds its model on the CPU.

## GPU optimisation (G2)

Measured on the free GPUs (2026-10-18) against the exact path of the code after G1 (`aeeba79`, frozen), the G0 set with three runs per case.

**Done, exact.**

- **Prefetch only where it pays** ([memory](/docs/development-memory)): `sequence` handles (autoregressive models; GPT-SoVITS's T2S is one now too) neither prefetch nor reserve room for copies in flight. Partly loaded (G1's caps), interleaved runs on a quiet GPU: Qwen3-TTS base-clone-en 24.6 → 16.2 s, VoxCPM v2-clone-en 29.0 → 13.6 s, CosyVoice v2-clone-en 10.1 → 7.4 s, each equal to no side streams, while F5-TTS and OmniVoice keep their prefetch. The audio is the whole model's.
- **CosyVoice's flow U-Net under `compute.compile`** recompiled at every request (its per-level attention mask was cached by the mask's identity, which torch.compile guards on): warm requests took 12.8 s instead of 1.0 s. Keyed by the U-Net's level now; compiled, 0.97 s; eager, the same audio as before.
- **IndexTTS's beam caches in one buffer** (done after the round, measured against `fc4b6b3`, two interleaved rounds): every layer's keys and values sit in one buffer, so a step's beam reorder is one copy per beam (one when no beam moved) and each layer writes its new key and value in place, instead of an `index_select` and a `torch.cat` per tensor, each copying it whole. Two buffers with room to grow take turns. Identical on the GPU and the CPU. Warm: v15-clone-en 0.58 → 0.54 s, v2-clone-en 2.02 → 1.93 s, v25-clone-zh 1.73 → 1.67 s; about 30 s of speech ×1.11–1.12 (1.5 4.79 → 4.29 s, 2 17.57 → 15.81 s); on the CPU ×1.02–1.05.
- **OmniVoice's packed guidance** (opt-in, request option `packed_guidance`, done after the round against `a552038`): each item's conditional and unconditional sequences in one row under a block-diagonal mask, instead of two rows padded to the conditional length. The exact path is unchanged (identical, the same speed). Packed, two interleaved rounds on a 3090: clone-en 0.77 → 0.61 s, finetuned-en 0.76 → 0.60 s (×1.26–1.27), clone-en-long 3.37 → 3.01 s (×1.12), design-en and auto-zh unchanged (0.54 s: no reference, little padding); the audio is another take (decisions flip under other rounding). On the CPU clone-en 24.0 → 18.3 s (×1.31), design-en ×1.02, both identical to the exact path.
- **Training under `lowest`** (done after the round, against `a1350b3`, Qwen3-TTS 1.7B's fine-tune on a 3090): its stage spent most of its time in the kernel, compacting memory for each transparent huge page AdamW's per-step temporaries took (sampled stacks: the step's `addcdiv_`), with the page cache filling the RAM. The rest of a step is CPU AdamW's arithmetic. Profiles of every trainer's standard fine-tune showed no data-loading cost; their host time is checkpoint writing (F5-TTS 4 s of a 9 s stage) and module initialisation draws, which the trainers replay as upstream made them.

## Memory modes and a real out-of-memory

The last gate of the memory work, measured on an RTX 3090 (2026-10-19): the G0 cases under `compute.vram_mode=high` and `none`, three runs each, against a fresh default round on the same GPU, and the contract suite under `none`.

| --- | --- | --- | --- | --- |
| Qwen3-TTS Base / CustomVoice | 1.27 s, 8.3 GB / 0.82 s, 4.0 GB | the same | 30.3 s, 2.1 GB / 19.1 s, 1.0 GB | identical |
| CosyVoice 2 / 3 | 1.05 s, 3.1 GB / 1.05 s, 7.4 GB | the same | 14.9 s, 0.8 GB / 12.4 s, 1.6 GB | identical |
| F5-TTS | 0.91 s, 0.8 GB | the same | 2.06 s, 0.2 GB | identical |
| Fish Speech S2 Pro | 3.23 s, 9.9 GB | the same | 106 s, 1.6 GB | identical |
| GPT-SoVITS v2 / v4 | 0.64 s / 1.06 s | the same | 0.95 s / 2.34 s, 0.3 / 0.6 GB | identical |
| IndexTTS 1.5 / 2 | 0.55 s / 1.94 s, 8.2 GB | the same | 7.7 s / 30.8 s, 1.5 GB | identical |
| OmniVoice | 0.78 s, 2.0 GB | the same | 2.15 s, 0.6 GB | identical |
| VoxCPM 1.5 / 2 | 0.97 s / 2.14 s | the same | 8.8 s / 23.6 s, 1.0 GB | identical |

`none` streams every unit in every phase, so a model runs in a tenth to a fifth of its memory; an autoregressive one copies its streamed layers for each token, which is where its time goes, while the small ones (F5-TTS, OmniVoice, GPT-SoVITS) stay within about 2.5×. The contract suite under `none`, every installed model on `cuda:1`, the licence-gated ones included: 165 passed (3 skipped: models that do not stream), 3 h 20 min.

**A real out-of-memory**, not the test's injected one: under an 8 or 12 GB cap with the allocator capped as well, a thread took the remaining memory while a request was generating, down to 64 KB fragments. Qwen3-TTS's talker and IndexTTS 2's GPT (at two moments) ran out in the allocator itself, ran again with half their weights streamed (`oom_retries`, the warning, `meta.memory.partial`: "capped at half its weights after running out of memory"), and gave the undisturbed run's audio sample for sample. Taken a moment later, after the talker had finished, the same squeeze made the codec decoder's placement see 218 MB free and the talker give up memory instead: no error, the same audio. (`compute.vram_limit_mb` alone tells the runtime, not the allocator: the squeeze then took the whole GPU, which is why the allocator was capped for this.)

## Not done because it changes results

- bf16 or quantised weights, another thread count, the tanh form of GELU, SDPA's grouped-query path for Fish Speech's repeated heads, a static KV cache by default.
- Truncating VoxCPM's attention to exactly the filled positions: identical in bf16, not in fp32 (the kernel's blocks change); the cut at a multiple of 256 is identical in both.
- `foreach=True` Adam/AdamW: identical for float32 parameters but slower on the CPU (1032 against 748 ms a step for 100 tensors of 2048 × 2048; Qwen3-TTS's training ×0.92). `fused=True` AdamW: its results differ.
- Caching weight norm within a step for GPT-SoVITS's discriminators: the gradients would sum in another order.
- For Qwen3-TTS on CUDA: a static cache bucketed by 256 with a mask (another SDPA kernel), and batching a long text's segments (other draws).
