Every engine runs in the server's own process (or in the command's, on the command line), on Mizuoto's own runtime: `mizuoto/runtime/`, a small framework in the manner of ComfyUI's model management. The core reaches it only through `mizuoto/core/inference/`. This page covers both sides: what an engine gets from the runtime, and how the core calls a loaded model. How to write an engine is in [Adding an engine](/docs/development-engine).

## Who is where

| Part | Code | Role |
| --- | --- | --- |
| `InferenceService` | `mizuoto/core/inference/service.py` | Builds the `Runtime` on first use, from the `compute` settings; says which engines are implemented here, what an engine is missing (`torch`, `mizuoto-fishspeech`…), its extras and its trainer |
| `RuntimeService` | `mizuoto/core/inference/runtime.py` | One engine per (engine, device), made on demand; `loaded()` gives a model's `EngineHandle`; `max_resident_models`, the idle reaper, `runtime_changed`, the doctor |
| `LocalEngine` / `LocalHandle` | `mizuoto/core/inference/local.py` | One engine on one device in this process, and the handle of one of its loaded models |
| `RemoteEngine` / `RemoteEngineHandle` | `mizuoto/core/remote/client.py` | The same, for a device named `<host>/<device>`: a session with `mizuoto agent` on another machine |
| `EngineHandle`, `EngineRequest`, `ModelRef` | `mizuoto/core/inference/engine.py` | What the core holds and passes: standard library only at module level |
| Task types | `mizuoto/core/inference/tasks.py` | `SynthesisTask`, `VoiceSpec`, `Reference`, `LoadSpec`, `AudioChunk`, `Description`… (standard library dataclasses) |
| `Engine`, `LoadedEngine`, registry | `mizuoto/runtime/engine.py` | The engine contract; `BUILTIN` and the `mizuoto.engines` entry points |
| `RequestContext` | `mizuoto/runtime/context.py` | One per call: cancel, generators, progress, text pieces, scratch |
| `Runtime` | `mizuoto/runtime/runtime.py` | What `Engine.load` gets: `devices` (`DeviceService`), `manager` (`ModelManager`), `options` (`RuntimeOptions`) |

`TtsService`, `AsrService` and the voice service never see a `LocalEngine`: they call `RuntimeService.loaded(ModelRef, device, dtype, options, request)` and use the handle it returns. Local or remote makes no difference to them.

## The runtime

`InferenceService.runtime` builds one `Runtime` per process the first time a model loads, so a command that never loads a model imports none of it.

### Devices: `device.py`

`DeviceService` is the device half of ComfyUI's `model_management.py`, as an object instead of module globals. Device names are Mizuoto's: `cpu`, `cuda:N` (NVIDIA, or AMD on ROCm), `xpu:N`, `mps`; resolving `auto` is the core's job (`ComputeService.resolve_device`). Engines get a real `torch.device`; nothing narrows `CUDA_VISIBLE_DEVICES`.

- `memory(device)`: (free, total) bytes; on CUDA, memory torch holds but does not use counts as free.
- `empty_cache(device)`, `synchronize(device)`.
- `supports(device, dtype)` and `pick_dtype(device, requested, supported, cpu)`: the dtype a component runs in, from the user's `engines.<id>.dtype` and the engine's preference order (fp32 on the CPU unless asked; GTX 16xx cards are kept off fp16).
- `is_oom(error)`: whether an exception means a device ran out of memory, without importing torch.
- `float64_device(device)`: where a module that computes in float64 runs, the device or the CPU when it has no float64 (MPS, XPU without fp64). `pin_to_cpu(module)` keeps such a module on the CPU when its parent moves; CosyVoice 3's F0 predictor uses both.
- `probe_devices()`: the accelerators torch sees (CUDA, ROCm by HIP, XPU, MPS) with their memory. The core's probe (`mizuoto/core/compute/probe.py`) asks `nvidia-smi`, `rocm-smi`/`amd-smi` and the platform first, and torch only in a child process (`python -m mizuoto.runtime.device`) when the installed build could find a GPU they did not, or in this process once the runtime has loaded torch.
- An engine's `DEVICES` (every kind by default) mirror its manifest's `devices`; `torch.compile` runs eagerly on MPS.
- `torch_build()`: what the installed torch was built for and which accelerators work here (`mizuoto doctor`).

### Model handles and the model manager

A `ModelHandle` (`handle.py`, ComfyUI's `ModelPatcher` without the diffusion parts) wraps one `nn.Module` with weights: its `name` (shown in the loaded-models list, e.g. `omnivoice/omnivoice:model`), `load_device`, `offload_device` (the CPU), `kind` (`sequence` for an autoregressive LM, else `oneshot`) and its sizes (`size_bytes`, `loaded_bytes`, `streamed_bytes`, `host_bytes`). The engine only reads `module`; a `LoadedEngine` lists its handles in `self.handles`.

The `ModelManager` (`manager.py`, ComfyUI's `load_models_gpu` / `free_memory`) keeps every registered handle with its owner (`<model id>@<device>`) and last use, and places handles **whole or partly** for each phase of a request (`ctx.use`, `ctx.run`): idle components give up memory unit by unit, a model that does not fit keeps part of its weights in RAM and streams them to the device as its layers run, and a phase that runs out of memory runs again, exactly, with more weights streamed. The policy (`policy.py`, `VramPolicy`) comes from the `compute` settings at each load.

| Method | Use |
| --- | --- |
| `register(owner, handles, mode, pinned)` / `unregister(owner)` | After a load; when the model is unloaded (frees without copying back) |
| `use(handles, memory_required)` | Around each phase, or the whole call for an engine without `PHASED` |
| `after_oom(handles)` | `ctx.run`'s clean-up before a retry |
| `release_idle(device)`, `drop_host_copies()` | Free a GPU (before a fine-tune, after running out of memory); RAM is short |
| `resident()`, `owner_usage(owner)`, `owner_placements(owner)` | The loaded-models list, `meta.memory` and its `partial` report |

Phases, the budget and VRAM modes, units and streaming, host copies, eviction, the exact retry, working-memory estimates and their calibration, and how an engine takes part: [Memory](/docs/development-memory).

On the CPU nothing is moved and nothing is counted, unless `DeviceService(simulate={"cpu": bytes})` makes it play a GPU (tests and the parity harness: `compute.simulate_vram_mb`).

### Layers, attention, loading

- **`ops.py`**: every engine builds its modules from an `ops` namespace instead of `torch.nn`. `ops.default` has the same layers with **no random initialisation**: constructing a large model takes no time and draws no random numbers, so loading never touches an RNG. `ops.cast` also casts weights to the input's dtype and device on every forward, for a component stored in one dtype and computed in another. `init_random(module, generator)` gives a `default` module real weights in tests.
- **`accel/`**: every attention computation in native code is `accel.attention(q, k, v, *, site=SITE, mask=…, causal=…, scale=…, enable_gqa=…, dropout_p=…, mask_info=…)`, never a direct call to SDPA (an architecture test forbids that outside `runtime/accel`). Each `Site` holds its **reference**, the exact computation upstream made there; with `compute.attention = auto` (the default) the reference runs, bit for bit. Another setting binds a policy that chooses among SDPA's kernels, FlashAttention, xFormers and SageAttention per call, with compatibility checks and fallbacks; `features.apply` sets the host's `compute.fast` switches, the one place native code sets `torch.backends` flags. See [Acceleration](/docs/development-acceleration#attention).
- **`loading.py`**: `load_state_dict` (safetensors, or a pickle with `weights_only=True`), `strip_prefix`, `replace_prefixes`, `fold_weight_norm`, and `load_into`, strict by default: a missing or unexpected key is an error naming it, unless the engine lists it as ignorable.
- **`sampling.py`**: `hf_sample` / `hf_process`, transformers' logits processors in transformers' order (repetition penalty, min new tokens, suppression, temperature, top-k, top-p), then `multinomial1`, `torch.multinomial`'s own computation on the request's generator without its waits for the device, so a seeded draw matches ([sync-free sampling](/docs/development-acceleration#sync-free-sampling)).
- **`lm/`**: `QwenDecoder` (the Qwen2/Qwen3 decoder with transformers' numerics and parameter names, `mask_for`, `hf_sdpa`), `DynamicCache`, the opt-in `BufferCache` (`compute.kv_cache = static`) and `peak_bytes` for working-memory estimates.
- **`graphs.py`**: `Graphs`, `LayerSteps`, `DecoderSteps`: decoding steps captured as CUDA graphs that replay the eager kernels (`compute.cuda_graphs`), see [CUDA graphs](/docs/development-acceleration#cuda-graphs-computecuda_graphs).
- **`convert/onnx.py`**: an ONNX graph's nodes and tensors read from the protobuf wire format, without the onnx package (CosyVoice's speech tokenizers and CAM++, GPT-SoVITS's G2PW).
- **`compile.py`**: `Compiled` / `compile_module(module, enabled, name)` wrap one hot module in `torch.compile(dynamic=True)` when `compute.compile` is on; engines call `compiled or module`, and any compiler error falls back to eager. See [`torch.compile`](/docs/development-acceleration#torchcompile-computecompile).
- **`policy.py`, `units.py`, `stream.py`**: the VRAM policy, a model's streamable units, and the per-device `Streamer` ([Memory](/docs/development-memory)).
- **`snapshot.py`**: `snapshot()` digests the process-wide state an engine call must leave alone; the contract suite compares it before and after requests.

The building blocks engines share live beside the runtime: `mizuoto/nn` (DSP bit-exact with torchaudio, librosa and Whisper; flows; transformers; vocoders; codecs; SSL and speaker encoders) and `mizuoto/text` (BPE tokenizers identical to transformers' for the models Mizuoto runs, Whisper's vocabulary, wetext's normaliser).

## The request context

Each call to an engine gets one `RequestContext` (`mizuoto/runtime/context.py`):

| Member | Purpose |
| --- | --- |
| `check_cancel()`, `cancelled()` | Cooperative cancel. `check_cancel()` raises `Cancelled`, a `BaseException`, so model code's `except Exception` cannot swallow it. Engines call it at every token or ODE step |
| `bind()` | Makes the context the running thread's request; layers then call the module-level `check_cancel()` without being handed it |
| `generator_for(device)`, `generator` | The request's `torch.Generator` on a device, one per device, seeded with the request's seed (fresh entropy without one) |
| `rng` | The request's `random.Random`, seeded the same way |
| `reseed(seed)` | Start the request's streams again (an engine that reseeds per segment, as GPT-SoVITS's upstream did) |
| `progress(stage, value, message)` | `loading:<part>`, `generating`, … |
| `applied`, `warn(message)` | The parameter values the engine actually used, and its warnings: both come back with the result |
| `text_pieces()` | Streamed text as the client sends it (`SynthesisTask.text_stream`): a real generator, safe on another thread, ending early on cancel |
| `tmpdir` | A scratch folder under `<cache>/scratch/<engine>/`, removed when the call ends |
| `use(handles, memory)`, `run(name, handles, fn, memory, generators, fallback)` | A phase of the request: its components placed with room for its working memory; `run` adds the exact retry after running out of memory and the optional fallback ([Memory](/docs/development-memory#phases)) |
| `accel` | The model's attention policy, bound with the context ([Acceleration](/docs/development-acceleration#policies)) |
| `log`, `device`, `seed`, `request_id` | |

## Global state

Engines share one process with the server, each other and the tests, so native code **changes nothing process-wide**. `test_native_code_leaves_global_state_alone` forbids, in `runtime`, `nn`, `text`, the engines and the gated packages:

- seeding a global RNG: `torch.manual_seed`, `torch.cuda.manual_seed(_all)`, `random.seed`, `np.random.seed`;
- `os.chdir`, `sys.path.append` / `insert`, `os.putenv`, assignments to `os.environ`;
- `logging.basicConfig`, `torch.set_default_dtype`, `torch.use_deterministic_algorithms`, assignments to `torch.backends.*` and `torch._inductor.config`.

Randomness comes from `ctx.generator_for(device)` and `ctx.rng` instead. That is also what makes parity possible: a fresh `torch.Generator` seeded with *s* yields the same stream as torch's default generator after `torch.manual_seed(s)`, on the CPU and on CUDA (`scripts/parity/check_rng.py`), so an engine that makes upstream's draws in upstream's order on the request's generator reproduces a seeded upstream run draw for draw. Where upstream drew from the global generator while building or preparing something, the port replays those draws on a private generator rather than touching the global one.

Training stages are the one exception: they run in their own process and seed the process-wide generators there (see [Trainers](/docs/development-training)).

## LocalEngine: calling a model in this process

`RuntimeService.engine(engine_id, device)` makes a `LocalEngine` on first use and registers it with the `ComputeService` as the memory holder `engine:<engine>:<device>`. Its state is `stopped` (nothing loaded), `ready`, `busy`, or `crashed` when the engine's implementation failed to import.

**Loading** (`LocalEngine.load`):

1. `start()` finds the implementation with `get_engine(id)` (imports its module, not torch).
2. `make_room(model_id)`: the runtime service unloads the least recently used idle models beyond `compute.max_resident_models` (pinned models stay).
3. A `LoadSpec(model_id, model_dir, variant, device, dtype, options)` is built; `options` merges the engine's load options with `model_options(model_id)`, which adds the folders of the model's shared assets as `options["assets"]`.
4. `Engine.load(spec, runtime, ctx)` runs with the context bound, **outside** `torch.inference_mode()`; the handles are registered with the manager, and `describe()` is kept as the handle's `description`.

**Calls** (`LocalHandle.prepare_voice`, `synthesize`, `convert`, `edit`, `call`): each runs in the calling thread (a job's) inside `torch.inference_mode()`, with the context bound and the model's handles held by `manager.use(...)`. The seed is the task's `params["seed"]`.

<Callout type="warn" title="Why loading runs outside inference mode">

A CPU kernel trap found while checking E2-TTS against upstream: `F.linear` on a strided (non-contiguous) 3-D input takes another kernel when the weight requires grad, or when it is an *inference tensor* (made inside `torch.inference_mode()`), even under `no_grad`. Upstream's weights are ordinary parameters that require grad, so native engines leave parameters as `nn.Module` makes them (no `requires_grad_(False)`), and models are loaded outside inference mode. Requests still run inside it. The [engine reference](/docs/engines#rules-every-engine-keeps) has both traps.

</Callout>

### Streams are generators

`synthesize`, `convert` and `edit` return generators of `AudioChunk`. `LocalEngine.stream` drives the engine's own generator lazily: the engine runs only while the caller asks for the next chunk, and only then is it bound to the thread and in inference mode. Each chunk is checked (it must be an `AudioChunk`), turned into float32 mono numpy samples and handed on; the first one sets `timings["first_chunk"]`. The caller closes the stream (`contextlib.closing`) to stop early, which closes the engine's generator too. `TtsService` drains it chunk by chunk and forwards chunks to a `StreamSink` when the client streams.

### Cancel and timeouts

The caller passes an `EngineRequest` with its `cancel` event (a job's `cancel_event`), an optional `timeout`, the streamed-text queue (`text_input`, filled by `TextFeed`) and a `progress` callback. A small watcher thread checks every 20 ms: it copies the caller's cancel into the context's cancel event, and past the timeout it marks the call timed out and cancels it. The engine stops at its next `check_cancel()`; the call then fails with `CancelledError`, or `OperationTimeoutError` after a timeout. When the call ends, the handle copies `applied`, `warnings` and `timings["total"]` into the `EngineRequest`.

### Errors

What an engine raises becomes the core's error:

- `EngineError(message, detail, code)` keeps its code (`error_from_code`), with the engine and device added to the detail; `Unsupported` is `capability_not_supported`.
- Running out of memory (`is_oom`) offloads every idle component on that device (`release_idle`) and fails with `compute_unavailable`, `detail.reason = "out_of_memory"`; the job service then unloads every model not in use from every GPU (`release_after_oom`).
- Anything else is `engine_error` with the exception's name and traceback in the detail (and in the log).

## Memory

Memory is managed at three levels:

| Level | Who | What |
| --- | --- | --- |
| Components | `ModelManager` | Before each phase of a call, idle components on the same device give up memory, unit by unit, to make room; what does not fit streams from RAM ([Memory](/docs/development-memory)) |
| Models | `RuntimeService` | At most `compute.max_resident_models` (default 3) models stay loaded across all engines; before a load the least recently used idle one is unloaded. The server's reaper (every 10 s) also unloads models idle for longer than `compute.unload_after_minutes` (default 20; 0 = never) or `engines.<id>.idle_minutes`. `engines.<id>.pinned_models` are never unloaded to make room or for idleness |
| The process | `ComputeService` | Each `LocalEngine` is a memory holder: **Free GPU memory** (`POST /api/v1/compute/release`) unloads every model of every idle holder and offloads what is left; refused while a holder is busy |

Nothing refuses a model on an estimate of GPU memory: it always tries to load, and only a real allocation failure is an error. When a job fails for running out of memory (after the exact retries), `ComputeService.release_after_oom` unloads every model not in use from every GPU (ComfyUI's `unload_all_models`); models on the CPU stay. How components share a device below this level is in [Memory](/docs/development-memory).

A change to any `engines.<id>.*` setting unloads that engine's models (`unload_engine`), so the next request loads them with the new device, dtype or load options.

## Remote engines

When an engine's device is `<host>/<device>` (for example `engines.qwen3tts.device = "gpu-box/cuda:0"`), `RuntimeService.engine` asks `RemoteService` for a `RemoteEngine`: a session with the `mizuoto agent` on that host for one engine on one device. The agent is a whole Mizuoto with its own data folder, models and runtime; it runs the engine in its own process exactly as a host does. `RemoteEngineHandle` answers the same calls as `LocalHandle`. For the user-facing set-up, see [Remote engines](/docs/advanced-remote).

**Protocol 2** (`AGENT_PROTOCOL` in `mizuoto/core/remote/wire.py`) works at the level of a loaded engine. The frames are `mizuoto/core/remote/frames.py`'s (a 4-byte length, a kind, a JSON body or a JSON header plus raw bytes), over TCP or TLS:

1. The host connects and sends `hello` with the token (compared with `hmac.compare_digest`) and its protocol. An agent of another protocol refuses the host with a hint to install the same Mizuoto version on both machines, and the host refuses such an agent in turn. Otherwise the agent answers with its `AgentInfo`: version, devices, which engines are available there and its installed models.
2. `open {engine, device}`, then `load`, `prepare_voice`, `synthesize`, `convert`, `edit`, `call`, `unload` and `status`, one after another; `cancel` and `text` (streamed text) may come at any time.
3. The agent answers each operation with `progress`, `chunk` (a binary frame: float32 little-endian mono) and `file` frames, then a `result` or `error`, and beats every 5 s. With no frame for `remote.heartbeat_timeout` (60 s), the host closes the session with `worker_failed` (`during = "heartbeat"`); the next request reconnects.

**Files by content.** A path means nothing on the other machine. Every file a request names becomes `mizuoto-file:<sha256>/<name>`: `have` asks which the agent lacks, and `put` sends those in 8 MiB frames, checked against the SHA-256. The agent keeps them in `<cache>/remote/files/` and removes what no host asked for in a month. The folder a `prepare_voice` writes into becomes `mizuoto-out:…`; its files come back as `file` frames into the host's own folder.

The host plans against its own catalogue and the agent's model list; the agent handles its own GPU memory, and training always stays local.

## Seeing it: `mizuoto runtime` and `mizuoto doctor`

```bash
mizuoto runtime                 # the models loaded in the running server: engine, device, bytes, busy or idle
mizuoto runtime --unload        # unload every model not in use
mizuoto runtime qwen3tts/1.7b-base --unload
mizuoto doctor                  # torch against the hardware, every engine, its extras
mizuoto doctor gptsovits --json
```

- `mizuoto runtime` asks the running server (found through `server.json` in the data folder), since its process holds the models; without a server it reports the command's own process. The same is `GET /api/v1/runtime` and `POST /api/v1/runtime/unload`, and the web UI's **Models in memory** sheet (`LoadedModelsSheet`).
- `mizuoto doctor [ENGINE]` is `RuntimeService.doctor`: the installed torch build against the machine's hardware (CUDA, ROCm, XPU, MPS, CPU) with the install command for the right build (`mizuoto/core/compute/torch_index.py`), each engine available or missing (and what is missing), optional extras that do not import (`Engine.EXTRAS`) and a trainer's missing requirements. The same is `GET /api/v1/runtime/doctor` and `GET /api/v1/engines/{id}/doctor`.
