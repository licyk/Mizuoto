Fish Speech

Mizuoto 单独发行包 mizuoto-fishspeech 中实现的 Fish Speech 引擎：S2 Pro 的双自回归 transformer 与 44.1 kHz 编解码器，Drama 3 的混合专家主干与码本塔，哪些做法与上游完全一致，每帧只等待设备一次与 CUDA 图，按行流式加载的专家，LoRA 微调，以及对照结果。

Fish Audio S2 Pro 与 Drama 3（fishaudio/fish-speech）。S2 Pro 及其移植版采用 Fish Audio Research License；Drama 3 及其移植版（mizuoto_fishspeech/drama3，移植自 fish-speech 0f8a12e8）采用 Fish Audio Community License 1.0（见 Drama 3）。移植版受这些许可约束，所以作为单独的发行包发布：mizuoto-fishspeech（packages/native/fishspeech，包名 mizuoto_fishspeech，附 LICENSE.md 与 drama3/LICENSE.md），注册在入口点组 mizuoto.engines 下（fishspeech = mizuoto_fishspeech:FishSpeechEngine）。下载模型和合成都需要先接受许可。在 CPU 上以 fp32、相同种子运行时，它的编码和音频与 Mizuoto 0.1 所运行的上游带种子 generate_long 完全相同，训练器导出的模型与 0.1 逐位相同。面向用户的说明见 引擎详解。

变体与文件

两个变体。s2_pro（目录模型 fishspeech/s2-pro，本页 Drama 3 之前的内容都关于它）：用一到四段参考音频克隆，每段都带参考文本；行内标签；说话人之间的对话（<|speaker:i|>）。模型目录中有 config.json、权重（model.safetensors.index.json 及其分片、model.safetensors 或 model.pth）、codec.pth 和 BPE 分词器文件。音色缓存是 codes.pt，即每段参考音频的编码。

精度：与上游相同，CUDA GPU 上用 bf16；其他设备用 fp32（bf16 在 CPU 上是模拟的，慢得多）；engines.fishspeech.dtype 可以覆盖。

工作原理

提示是一段 ChatML 对话：一条系统消息，包含每段参考音频的文本及其编码，然后是要说的文本。慢 transformer（Qwen3-4B 的形状：36 层，q/k RMSNorm，一个融合的 wqkv）生成每帧的语义 token；快 transformer（4 层）根据慢模型归一化后的隐藏状态生成其余九个码本。编解码器（改造过的 44.1 kHz DAC：因果卷积、窗口化 transformer、下采样残差量化器，含一个 4096 的语义码本和九个 1024 的码本；约每秒 21.5 帧）编码参考音频，并把帧解码成音频。文本按说话人轮次分批生成，每批完成即解码。

与上游一致的做法

  • 提示是上游的对话，每个文本部分单独分词；每帧的主 token 是 semantic_begin_id + code。
  • 采样按上游的顺序从请求的生成器抽样：主 token 抽两次（先用请求的温度和 top-p，再用 1.0 和 0.9 做重复感知采样），然后是快 transformer 的九次抽样。一次抽样就是 argmax(probs / -log(u))。top-k 固定为 30，与上游相同。
  • 数值：Fish 的 RMSNorm 在 float32 中计算；RoPE 作用于相邻元素对，频率表舍入到 bfloat16；预填充用带布尔因果掩码的 SDPA，解码步骤用 SDPA 的 math 内核（直接调用，不改进程级设置；布尔掩码先变成加性掩码，与 F.scaled_dot_product_attention 的做法相同：直接给内核布尔掩码时，它会把掩码当作数值相加；在 0.2.6 之前每一步的分数都被加了 1，CPU 上编码相同但数值位不同，GPU 上 bfloat16 下则是另一次生成）；快 transformer 用手写的 softmax。权重归一化保留检查点的两种格式，并在每次前向时重新计算，与上游相同。
  • 参考音频用 torchaudio 的内核重采样到 44.1 kHz。
  • WAV 输出。 codec_decode 用 nn.dsp.wav.write_wav 写 WAV，与 soundfile.write 逐字节相同：libsndfile 1.2 存储裁剪后的 lrint(x × 2³¹) >> 16，也就是 floor(x × 32768)，只有略低于一个台阶的值例外。codec_encode 只读 WAV。

有意的差异

  • 没有守护线程，也没有预分配 32 768 个位置的缓存。 缓存通过拼接增长；经过 repeat_interleave 后，键和值就是上游构造的那些张量。注意力掩码按调用生成，而不是上游那 4 GiB 的掩码缓冲。
  • 不构建上游从不运行的编解码器模块。 上游的编解码器为解码器第一个块构建了一个 transformer，却从不接上它（没有权重，从不运行）。codec.pth 里还有旧版上游保存的 RoPE 表和掩码，上游已不再加载，这里也忽略。
  • 接受但无效果：normalize 和 repetition_penalty 在上游的推理路径中不起任何作用，所以这里也不起作用。
  • 在 GPU 上编码参考音频。 上游在 GPU 上以 bf16 加载编解码器，而 encode_reference 传给它 float32 的音频，所以在 GPU 上克隆会失败（Input type (float) and bias type (c10::BFloat16) should be the same；已用 0.1 在 RTX 3090 上复现）。移植把参考音频转换为编解码器的精度；在 CPU 上（fp32）没有任何变化。
  • GPU 上的 Snake 是上游的 TorchScript 函数，按 TorchScript 的方式计算，而不是按即时执行同样的代码来计算：
    • 在 autocast 下（以 bf16 或 fp16 解码）全程以 float32 计算。即时执行的 autocast 会让 alpha · x 和正弦保持低精度；移植在 mizuoto-fishspeech 0.3.3 之前就是这样，在 RTX 3060 上它解码的音频与上游最多相差 0.036。
    • 没有 autocast 时（编码参考音频）各运算原地执行，结果相同。
    • 与上游对比： 关闭 TorchScript 的融合器时，在 RTX 3060 上以 bf16 运行，移植的编解码器给出与上游逐位相同的参考编码和解码音频（Drama 3 的 codec.pth，S2 Pro 用的是同一个文件；三段音频）。
    • 上游的融合内核： 从某个形状的第二次调用起，上游的 TorchScript 会融合 Snake，这会改变舍入，并取决于进程之前运行过什么。与之相比，解码音频相差在 0.01 以内，参考编码约五分之一不同。按融合内核的方式以 float32 计算 Snake 并只舍入一次，仍有 8–14 % 的编码不同，所以没有哪种固定的计算能跟上它。

显存与速度

阶段：编解码器编码参考音频并解码每批帧；语言模型（kind="sequence"，快 transformer 为 hot）生成每一批，生成继续时重新放置。每批的工作内存是慢模型缓存的真实上限：参考音频的编码、每个文本 token、之前各批的帧和 max_new_tokens，不超过 max_seq_len。在默认设置下（bf16），S2 Pro 最多占用 10.2 GB 显存（性能 上的 G13）；不够时运行时会流式加载部分权重。开启 compute.oom_fallback 时，如果编解码器解码显存不足，它的卷积解码器按 256 个潜在帧（约 3 秒）一块解码，每块之前带上第一个样本所依赖的 20 帧（解码器是因果的），量化器部分整段运行：与整段的样本只差求和的舍入（GPU 上 bf16 下 SNR 40 dB，而 bf16 与 float32 相比为 37.9 dB），60 秒只需 275 MB 而不是 5 GB。

一帧是一次慢 transformer 步骤加十个码本。原本的循环每帧约等待设备 22 次：轮次结束检查；把非语义 token 的码本嵌入置零的掩码赋值（vq_sum[~mask] = 0 会把掩码读回）；用列表下标取快 transformer 的掩码和旋转编码行（每个码本两次拷贝到设备）；采样器中把 Python 布尔值存入设备张量，每次抽样两次。它们都换成了完全等价的写法（torch.where、切片、fill_），解码步骤的掩码直接按它本来的样子生成为一行全真。每帧只剩一次等待。

开启 compute.cuda_graphs（NVIDIA，模型完整位于设备上）时，generate.Decoder 为每个已加载的模型保留固定张量：慢步骤在两次注意力调用之间的每一段作为一个 CUDA 图运行（LayerSteps），该帧的抽样、重复感知采样和快 transformer 作为一个 CUDA 图。采样设置是按请求填充的设备张量，所以一套 CUDA 图服务所有请求。编码完全相同，解码循环每帧快 2.2–2.5 倍。

在空闲的 RTX 3060 上，使用 CUDA 图时完整模型的一帧约需 64 毫秒。其中约 50 毫秒用于以接近显卡带宽的速度读取 16 GB 权重；其余大部分是数千个小内核。compute.compile（可选，不精确；fused.py）把它们融合：它在同样的 CUDA 图里编译每层注意力前后的两半、缓存上的注意力、这一步的嵌入和输出头以及采样的概率；关闭时即时执行的代码不变。这样每帧快 1.15 倍。采样不变，但概率的最后几位不同，所以语音是同一文本和音色的另一次生成，在相同种子下仍可重复，并通过契约测试。它只在模型完整位于其设备上时运行，输出会注明（applied["compile"]）。详见加速。

训练

方法 lora（阶段 tokens、train、export）：上游的 extract_vq、build_dataset，以及基于 Lightning + Hydra、使用 loralib 的 train.py 和 merge_lora，但不需要这些库，也不需要 protobuf。以相同方式播种时，它在 CPU 上的编码、损失、LoRA 权重和导出的 model.pth 与 0.1 逐位相同，导出的其他文件逐字节相同。（0.1 从不播种，所以只有第一步能复现。）它在所有设备类型上都能运行。

  • 跳过初始化抽样。 上游在加载检查点之前先用随机权重构建模型，并在抽取 A 之前把每个 loralib 层初始化两次：约 18 G 次抽样。initial_lora 只根据形状算出这些抽样让生成器前进多少（float32 的 normal_ 或 uniform_ 前进其大小，大小不是 16 的倍数时 normal_ 再多 16），然后在 GF(2) 中把 MT19937 向前跳（mizuoto.training.rng）：用 2 秒而不是 40 秒的抽样得到同样的状态，在加载权重的同时在另一个线程中计算。随后是加载器的基础种子和每一步的 LoRA dropout 掩码。
  • 与上游相同的混合精度。 检查点中的张量按上游的方式赋值，所以 S2 的归一化层保持 bfloat16，而 LoRA 层持有 float32 副本。
  • 保留：上游的训练前向不像推理那样把码本嵌入乘以 1/√11；预热让第一步的学习率为 0，B 从零开始，所以前两步的损失相同。
  • 填充。 整理器用 <|end_of_text|> 填充，而 S2 的词表里没有它：上游实际以 0 填充，Mizuoto 也是。
  • 导出是上游扁平的 dual_ar 形式（config.json + model.pth），0.1 和 Mizuoto 都能加载。最后一轮验证被跳过（它不改变任何保留下来的东西）。
  • training.memory：上游的逐层检查点保持原样；在 bf16-true 下，LoRA 层直接把检查点自己的 bfloat16 张量当作冻结的权重（从 safetensors 文件内存映射，不复制：数值相同），导出的键顺序从一个在 meta 设备上构建的模型中读取。在 S2 Pro 上实测（2026-10-19，RTX 3090）：训练阶段的进程加载时只占 0.4 GB 自有内存（用 bfloat16 副本时为 8.9 GB，用 float32 副本时为 17 GB），常驻峰值 5 GB；导出阶段持有合并后的权重 9 GB，另有映射的检查点（页缓存）。lowest 下，LoRA 线性层的冻结权重留在锁页内存中，每次矩阵乘法时复制到 GPU（streamed_linear，模型放到设备时不带它们）：结果相同（在 CPU 上比较微型训练器的损失值和 LoRA 权重）；S2 Pro 的 LoRA 在批量 2 下峰值从 15.6 GB 降到 7.9 GB（RTX 3060，经其 PCIe x4 链路每步 15.6 秒），默认批量 4 估算为 12.6 GB。

对照结果

在 CPU 上以 fp32 运行时，编码与上游带种子的 generate_long 相同；分词器、参考音频的重采样和编码以及编解码器的解码也都相同。两个完整链路用例（英文和中文克隆）逐采样相同；另外两个用例让每种实现加载另一种实现的导出，结果也相同。契约套件通过（6 项测试）。

限制

  • 完整运行模型（S2 Pro）需要约 10 GB 显存；在 CPU 上以 fp32 运行，速度慢。
  • normalize 和 repetition_penalty 没有效果（与上游相同），top-k 不能更改。
  • 结果受 Fish Audio Research License 约束：不可商用，也不能用于训练其他引擎。

Drama 3

变体 drama3，目录模型 fishspeech/drama-3（fishaudio/drama-3 的 78e5ab79，41.5 GB：专家为分块 FP8 的权重，以及 S2 的 codec.pth，与 S2 Pro 的逐字节相同）。移植自 fish-speech 0f8a12e8（fish_speech/models/text2semantic/fish_omni 与 generate_long_drama3），即 mizuoto_fishspeech/drama3。它用一到四段参考音频克隆（每段带参考文本），没有参考音频时用自带的音色说话，接受写在文本中的指示（[whispering]、[laughing]、<whisper>…</whisper>），最多十六个说话人（<|speaker:0|>…<|speaker:15|>；参考文本可以以其说话人标签开头）。许可：Fish Audio Community License 1.0，是该变体自己的许可（variants.drama3.licence）；接受引擎的许可即同时接受两份，它的结果标记为 fish-audio-community。

工作原理

模块内容
drama3/config.pyconfig.json：主干的文本配置、码本塔的配置、语义区间，按上游的方式检查
drama3/layers.py零中心 RMSNorm、部分 RoPE（前后两半）、带门控的 softmax 注意力、Gated DeltaNet（先一个因果深度卷积，再门控 delta 规则：提示按 64 一块分块计算，之后逐 token 递推）
drama3/moe.py每层 256 个路由专家（每个 token 用 8 个）和一个带门控的共享专家；专家堆叠存放，保持 FP8，按行流式加载
drama3/backbone.pyQwen3.5-MoE 的混合文本模型（40 层，每第四层为 softmax 注意力）及其 lm_head；加载逐专家的 FP8 张量
drama3/tower.py码本塔：4 个共享层和 9 个残差层，在帧序列上做注意力，每个残差层的输出头抽取下一个编码；两种采样器
drama3/prompt.py提示（一段对话：带 [Reference i] 块的系统轮、作为已完成轮次的前面片段、未结束的语音轮），文本检查，长文本切分及其历史
drama3/generate.py以 128 行为一块的预填充（同时以教师强制填充码本塔的缓存），解码循环（Decoder），一段接一段
drama3/steps.py解码步骤以围绕注意力调用的 CUDA 图运行（Stretches），及其固定张量
drama3/engine.pyLoadedDrama3：S2 的编解码器、参考音频处理与操作（继承 LoadedFishSpeech），加上主干和码本塔

一帧是十个编码：主干根据已有的帧预测该帧的主 token（轮次结束，或一个语义 token，它在区间中的位置就是编码 0），提示中每一行的嵌入是其 token 的嵌入，音频行再加上它的编码 1（乘以 1/√2）。然后码本塔接过主干的隐藏状态，逐个抽取编码 1–9，每个编码一个残差层；第一个共享层还会看到上一帧的编码 2–9。文本按约 300 个 UTF-8 字节、每段最多三个说话人切分（先按句末，再按分句标点，再按空格；不会切开标签或方括号），每段生成时都把第一段和最近一段作为历史放进提示；single_chunk 一次生成全文。

与上游一致的做法

在 CPU 上，上游的模块与移植版给出的隐藏状态、logits、帧和音频逐位、逐采样相同（见下文 对照结果）。具体包括：

  • 每个运算都按上游的顺序：归一化在 float32 中计算，旋转表每次调用时计算，delta 规则对提示用分块形式（每块 solve_triangular），对单步用递推形式，GQA 注意力（单个查询行时把每个键头的查询头折叠成行；多行时重复键头）经 mizuoto.runtime.accel.attention 以 SDPA 和布尔掩码计算，码本塔的交错式 RoPE，以及 float16 下输出为 float32 的下投影；float16 下专家先在 float32 中反量化并截到 float16 的范围再转换，与上游的稠密专家相同。
  • 专家：不超过 64 个（token, 专家）对时，对取出的专家做一次批量矩阵乘法（解码步）；更多时逐个专家计算，按专家顺序用 index_add_ 在 float32 中累加（提示）：两条路径的结果位不同，所以两者都保留。路由的 softmax 和 top-k 在 float32 中计算，权重重新归一化。
  • 提示：每段字面文本单独分词，参考音频按上游的方式检查和加标签；切分（上游测试中的用例即本包的测试）和历史（固定第一段，加上最近一段；提示超过 8192 行时从最旧的开始丢弃）。
  • 采样按上游的顺序从请求的生成器抽取：每帧先抽两次主 token（用请求的设置在“轮次结束 + 语义区间”上抽一次，再用 1.0、top-k 30、top-p 0.95 抽一次；第一次是最近 16 个主 token 中出现过的音频 token 时用第二次的结果），再抽九个编码。每次抽取是 argmax(p / E)，E ~ Exp(1)。sampler 选项可选用 Fish Audio 的参考采样器（reference_argmax / reference_ras，即上游的 --reference-sampling）：主 token 有 epsilon 截断（epsilon_cutoff，默认 0.001），任何重复的主 token 都会被替换（包括轮次结束），编码只从编解码器的 1024 个中抽取。
  • 上游的限制：提示最多 8192 行，总共最多 10 240 行（上游 CUDA 图的容量；每段的帧数被截到剩余的行数），默认值与 Fish Audio SDK 相同（temperature 0.7、top-p 0.7、top-k 30、每段 1024 帧；max_new_tokens = 0 时为 600，single_chunk 时为 2048）。
  • 编解码器：S2 的编解码器，权重归一化在转换到模型精度之前先在 float32 中折叠一次（上游为 Drama 3 加载编解码器的 load_codec_model），在该精度的 autocast 下解码；参考音频也用它编码。

CUDA 图

开启 compute.cuda_graphs（NVIDIA GPU 且能完整容纳主干和码本塔：bfloat16 下约 44 GB）时，解码步骤以重放即时执行核函数的 CUDA 图运行（drama3/steps.py、generate.Decoder）。一步先是码本塔的图（输出头、该帧的抽样，13 层中每两次注意力调用之间一个图），再是主干对这一帧的图（10 个 softmax 注意力层中每两层之间一个图，其间的 Gated DeltaNet 层、路由和专家都在图内）。注意力调用在图与图之间即时执行，读取每步增长一行的缓存，所以缓存和注意力核函数都与即时执行的代码相同。每步只等待设备一次，读取该帧的主 token 以及 logits 是否有限。

  • 固定张量随已加载的模型保留：步骤的输入与输出（最后的隐藏状态、位置、上一帧、最近 16 个主 token（不足时以 −1 填充）、该帧及其标志），以及 Gated DeltaNet 层的状态：图会原地更新它们，每个请求从零开始。注意力层的缓存仍然属于各个请求。
  • 采样设置按即时执行的代码传入的方式捕获，即 Python 数值：CUDA 除以一个数时按乘以其倒数计算，除以设备张量时按真正的除法计算，改用张量会改变结果位。请求的 temperature、top-p、top-k、采样器或截断不同时，码本塔的图（14 次捕获）会重新捕获；主干的图保留。
  • 上游自己的图没有移植：它们为几个缓存长度（1024、2048、4096、10 240）捕获整步，在填充并加掩码的缓存上计算注意力，采样设置为设备张量，与上游自己的即时解码相比结果位不同。
  • 流式加载专家时即时解码：GPU 放不下整个模型时专家按行流式加载，而一步要复制哪些行要从设备读出，图无法等待它。
  • 在 CPU 上按 Graphs 的约定检查（每段先预热、再捕获，并恢复其状态，然后重放）：两种采样器、多段文本、后续请求以及改变设置时都得到即时执行的音频（test_the_step_as_graph_stretches_decodes_exactly_as_eagerly）。在 NVIDIA GPU 上，test_cuda_graphs_decode_exactly_as_eagerly_on_a_gpu（bfloat16 和 float16）与 test_a_failed_capture_falls_back_to_the_same_audio_on_a_gpu 在小模型上比较图与即时解码；没有 GPU 时跳过。

有意的差异

  • 设备与精度。 上游只在 NVIDIA GPU 上以 bfloat16 运行 Drama 3（SM80 之前用 float16，残差流为 float32）；它的入口拒绝 CPU 和 float32。移植版在所有设备上运行，在 CPU 上用 float32（与 S2 Pro 相同）：对照的基准是上游的模块原样在 CPU 上以 float32 运行的结果。
  • 专家保持 FP8，每次调用用到的专家在运行时反量化，上游在其 FP8 核函数不运行的地方也是这样做的；上游的另一条路径在加载时把全部专家反量化。两者给出相同的数值（小模型对照把两者都与移植版比较）：专家占 32 GB，而 bfloat16 下是 64 GB，float32 下是 129 GB。上游的 W8A8 核函数（Triton，SM89 及以上，它还把激活量化为 FP8）没有移植：它的结果不同，只能作为可选项提供，而且这里无法测量。
  • 没有多 GPU 分层，也不在请求之间保留缓存。 上游把层分布到最多四块 GPU 上，并按至今最大的请求保留缓存；这里由模型管理器放置各层（放不下的部分流式加载），每个请求有自己的缓存。两种方式下注意力都只读取已关注的前缀。
  • 非有限的 logits 与上游一样会被拒绝，但每帧只检查一次（在该帧唯一一次等待设备时），而不是每次抽取前检查。
  • 音频是各段音频直接拼接，不裁剪，与上游相同；S2 Pro 的引擎会裁剪每一批。该变体声明了 long_text，所以 Mizuoto 把整段文本交给引擎，上游的切分与历史都会生效（如果由 Mizuoto 切成单独的请求，历史就无法跨越它们）。
  • Mizuoto 对所有引擎都会做的预处理在这里同样适用：文本和每段参考文本会去掉首尾空白；参考音频在音色库中存为单声道 16 位 WAV（浮点、24 位或立体声的音频会被转换，因此其编码可能与上游直接读取原文件时不同）；超过 30 秒的参考音频按 tts.reference_policy 截短；种子不能为负（上游取绝对值）。
  • 没有移植的：上游为 Drama 3 写的 CUDA 图（它们会改变结果位；Mizuoto 的图重放即时执行的核函数，见 CUDA 图），它的微调（上游在加入 Drama 3 时删除了训练代码，所以 LoRA 方法只适用于 S2 Pro），以及跨轮次的“导演式修改”（不在开源代码中）。

显存与速度

句柄：主干（kind="sequence"；每层两个单元，注意力为 hot，其次是 MoE；输出头为 hot）、码本塔（sequence）和编解码器。专家按行流式加载（开发：显存）：某层的 MoE 单元不常驻时，它的 256 个专家留在页锁定的主机内存中，每次调用只复制其 token 被路由到的专家（一个解码步：每层 8 个，约 25 MB；一个提示块：逐个专家），所以远小于模型的 GPU 也能运行。完整运行模型需要约 44 GB；其稠密部分（注意力、共享专家、嵌入和输出头、码本塔）在 bfloat16 下约 7.5 GB。每个请求的工作内存：softmax 层和码本塔对请求行数（最多 10 240）的缓存、DeltaNet 状态、一个提示块的激活值，以及一步反量化的专家。

在 CPU 上以 float32、16 个线程运行时，每帧约 2.1 秒，上游的模块同样如此（一秒语音是 21.5 帧：约 45 秒计算）；230 行的提示约 35 秒。在 GPU 上，放下整个模型需要约 44 GB，否则专家（30 GiB）从内存流式传输；内存也放不下时，放不下的那些层的专家保存在文件中（runtime.filemap，见显存）。2026-11-05 第一次在 GPU 上运行：RTX 3060（12 GB，PCIe x4），机器内存 31 GB，bf16：GPU 上 9.1 GB，锁页内存中 17.0 GB 专家，文件中 20.7 GB；预热后合成 5.5–8.3 秒语音用时 128–162 秒（每次请求向 GPU 复制 176–226 GB，1.4 GB/s），两次运行完全相同；其中 15–32 GiB 从磁盘读取，文件中的专家其余部分来自页缓存（72–87%）；可用内存从未低于 7.9 GB。

在 RTX 3060 上运行过一个随机模型，形状与真实模型相同，只有 8 个专家（2026-11-03，torch 2.8，bf16，设备上 8.5 GB）。每个 token 仍使用 8 个专家，所以一个解码步骤的工作量与真实模型相同。

  • 速度： 150 帧即时执行用 19.2 秒，使用 CUDA 图用 16.3 秒，快 1.18 倍（每帧 128 → 109 毫秒），音频相同。
  • 使用图时的帧： 每帧约 7,250 个内核，设备 97 % 的时间在忙。
  • 小型测试模型： 快 2.1 倍（每个请求 1.56 → 0.74 秒），音频也相同。

对照结果

与上游自己的模块（fish-speech 0f8a12e8）在 CPU 上以 float32、相同种子和线程数、真实模型对照（2026-11-01；工作区 experiment/fish-drama3，scripts/real_upstream.py、real_native.py、real_compare.py）：七个用例中，参考音频的编码、每段的编码和音频都逐采样相同：英文和中文克隆、无参考音频、行内标签（[laughing]、[whispering]）、两段参考音频的双人对话、参考采样器（reference_ras，截断 0.002），以及带历史、分两段生成的长文本（542 帧，25 秒）。对照之前先确认上游自身能完全重复。上游按其 TTSInferenceEngine 处理请求的方式运行（参考音频经它的加载器和编解码器，set_seed，generate_long_drama3，它的编解码器解码），移植版按服务器的方式运行（synthesize）。在小型随机模型上（scripts/tiny_parity.py），另外十二个用例（不限制 top-k、temperature 1.2 下 top-k 10、单段、max_new_tokens = 0、带成对标签的中文……）在 float32 和 bfloat16 下、与上游的 FP8 专家和反量化专家相比都相同，主干的隐藏状态和 logits 逐位相同。

对照上游源码的审查发现 Mizuoto 会自行切分 Drama 3 的长文本（已修复：该变体声明了 long_text），以及 float16 下专家没有截断（已修复），另有“有意的差异”中列出的请求层面差异。
